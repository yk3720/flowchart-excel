## 0. 本セッションで実装した内容（レビュー対象の前提）

第2回レビュー後、同セッション内でユーザー実機フィードバックに基づき以下を実装済み（未コミット）:

1. **「Excelに作成」ボタンの色**: プレビュー未生成/無効時は `STYLE_SECONDARY`（灰）、有効時は `STYLE_PRIMARY`（青）に切替。`_create_widgets()` 末尾で `_update_create_button_state()` を呼ぶよう修正（初期表示が決め打ち色のまま残るバグを修正）
2. **「表を読み込んでプレビュー」ボタンの色**: 白（対象未検出）/青（対象検出・未読込）/緑（プレビュー中）の3状態化。1秒間隔のExcel監視ポーリング（`_refresh_status_line`）に判定を統合
3. **描画位置のアンカー**: 「表全体」モードで外枠+タイトルを付ける際、外枠の外側の角が選択セルに一致するよう `frame_anchor_offset()` で図形群の原点をオフセット（以前は選択セル＝最初の図形の左上で、外枠がそこからさらに上・左にはみ出していた）
4. **フロータイトルの背景色**: タイトルのテキストボックスにのみ淡色グレー（`FLOW_SURFACE_SUBTLE`）背景を追加（外枠自体は白のまま）
5. **プレビュー空状態の文言**: 「プレビューデータを待機中…」→ 見出し「プレビューはまだありません」＋補足「Excelで表を選んだ状態で、上のボタンを押すとここに表示されます」（状態非依存の説明形にし、既に選択済みの場合とも矛盾しないようにした）

テストは46件全てパス、`dist/FlowchartExcel.exe` に再ビルド済み（webview同梱漏れなし）。

**【収束2周目のレッドチームレンズ指摘】** 上記5件はユーザーからの実機フィードバックを起点に修正したものだが、**修正後の実機再確認の記録はまだない**（テスト46件パス・再ビルド済みの記載のみ）。Phase 1a自体の完了条件には「実機で確認」を課しているにもかかわらず、その前提となる§0の5件に同水準の実機確認が無いのは非対称。次回セッションでPhase 1aに入る際、この5件についても実機確認を並行して済ませることを推奨する。

## 2. 改善点一覧（優先度別）

### P0: 実バグ（すぐ直すべき）

1. **【実装レンズ】`_refresh_status_line` の例外分岐でボタン色更新が漏れている**
   `app/ui/main_window.py:584-615`。正常系2分岐（Excel未起動／検出成功）では `_update_preview_button_color(...)` を呼ぶが、`except (AttributeError, pywintypes.com_error):` 分岐だけ呼び出しがない。セル編集中など実運用で頻発する状態でボタン色が直前の値に凍りつき、「押せば読み込める」と誤認させる。
   改善案: 例外分岐でも明示的に色を更新する（例: `has_target=False`）か、`_refresh_status_line` を「`has_target` を計算 → 成功/失敗どちらの分岐でも同じ変数で最後に一括更新」の形にリファクタし、更新し忘れる分岐を構造的に作れないようにする。

2. **【IxDレンズ、収束1周目の検証者レンズで実態がより深刻と判明】「Excelに作成」の有効/無効判定が二重実装でズレうる**
   Python側 `app/core/preview_payload.py` の `nodeCount`（`parse_table_rows` が独自に数えた値）だけを見て `embedded_preview.py` の `is_create_enabled()` がボタンを青くする一方、実際に描画できるかは **別リポジトリ** `c:/yk-application/flowchart-studio` の `lib/flowchart/graph/generate.ts` + `lib/flowchart/model/validate.ts`（`preview-web/vite.config.ts` の `@` エイリアス経由で参照）という別実装が判定している。「行はあるがバリデーションには落ちる」表（例: 接続先ID誤記）では、ボタンは青いのにプレビューは赤字「生成エラー」、という矛盾状態が起こりうる。
   **【収束2周目のフレッシュ第三者レンズが誤りを指摘・修正】** 当初「埋め込み1窓モードではエラー表示自体が非表示になる」と記載していたが、実装を確認したところ誤りだった。`App.tsx` の `{!embedded ? ... : null}`（148行目）が非表示にするのは**フッター**（2窓フォールバック専用のライブ更新説明文＋キャンセル/Excelに作成ボタン）のみで、生成エラーの見出し・詳細テキスト（93-100行目）は**ヘッダー**内にあり `embedded` の値に関わらず常に描画される。したがって埋め込みユーザーも「生成エラー」表示自体は見えている。ただし、ボタンの活性/非活性という**主導線の判定**と、ヘッダー内の警告表示という**副次的な手がかり**が分離しているため、ボタン色だけを見て操作するユーザーは見落としうる、という論点自体（一次論点＝判定の二重実装がズレうること）は実装で裏付けられており有効。
   **改善案の実現コストに関する注意（検証者レンズ、収束1周目）**: 当初案「作成できるかの最終判定をReact側（`generated.ok`）に一本化し、Python側はそれをホストに通知してもらってゲートにする」は方向性として妥当だが、**埋め込みモードのWebViewは`js_api=None`固定で生成されており、JS→Pythonの呼び戻しチャネルが現状存在しない**（`embedded_preview.py`の`_ensure_tkwebview2_compat`参照）。実装には新規のJS→ホスト通知経路（`js_api`追加、または`ExecuteScriptAsync`のコールバック経由での結果受け渡し）を新設する必要があり、一行の判定切り替えでは済まない。**Phase 1b**（P0-1のみのPhase 1aではない）着手前に、この経路をどう新設するかの簡単な設計を先に固めることを推奨する。
   **【収束2周目のレッドチームレンズによる重大度の再評価・ユーザー判断が必要】** 実際の失敗モードを`app/core/connector_manager.py:38-48`で裏取りしたところ、接続先ID不正な行があっても`connect_nodes()`は例外を投げず、`logger.warning("connector_target_missing...")`を出して当該の矢印だけを無言でスキップするのみ（クラッシュ・データ破損ではなく「矢印が1本サイレントに欠落する」程度）。この実害の軽さに対し、新規JS→Python通知経路の新設は明らかに重く、しかも新設しても"validate.tsはOKと言うがconnector_manager.pyは実際には一部描けない"という別種のズレが構造的に残りうる。**安価な代替案**: 新規アーキテクチャを増やさず、`connect_nodes`が既に出している`connector_target_missing`警告を集計し、描画完了後に「N件の接続を描画できませんでした」とメッセージボックスで通知する（実際の描画結果そのものを単一の真実源にする）。
   **判断が必要**: (a) 当初案通りReact側判定への一本化＋新規JS↔Python通知経路を新設する、(b) 安価な代替案（描画結果の警告集計＋事後通知）で実質的な実害だけ解消する、(c) 実害が小さいためP0から外しP1相当（中期課題）へ格下げして先送りする。いずれもユーザー判断が必要なため、Phase 1b着手前に確認する。

### P2: UX・ビジュアルの磨き込み（IxD・ビジュアル2レンズが独立に同種の問題を指摘）

- **【高】狭小画面（370×820px）内で4系統の非中立色（青/緑/黄/赤）が同時に動的表示され、"何が主操作か"の視線誘導が競合する**（ビジュアルレンズ。色の**意味の重複**とは別軸の、視覚的ノイズの量そのものの問題。収束1周目のフレッシュ第三者レンズが本文からの欠落として指摘し追加）
- **色の意味が重複・衝突**: 緑が「プリセット一致」と「プレビュー中」の両方に使われる。白が「対象未検出（押せる）」と「disabled（押せない）」の両方に見える（`STYLE_WHITE` #ffffff と `STYLE_SECONDARY` #f1f5f9 の差がほぼ判別不能）。CTk側は無効時に色相が変わるのに、Reactフォールバック版は同じ青を `opacity-40` で薄くするだけ、と無効表現の文法が不統一
- 3色ボタン（白/青/緑）の意味を説明する手がかりが画面上にどこにもない
- **メイン「表を読み込んでプレビュー」ボタンの色が、自分が押していない操作（その他▾→選択範囲を確認して作成）でも変わる**（`preview_active` がモード共通の単一フラグのため。IxDレンズ。収束1周目のフレッシュ第三者レンズが本文からの欠落として指摘し追加）
- 「キャンセル」(黄 `STYLE_WARNING`) と「✋中止」(赤 `STYLE_DESTRUCTIVE`) の色の強度が実際の重大度と逆転している（キャンセルは非破壊、中止は処理停止という重大操作なのに黄の方が目立つ場合がある）
- 「その他▾→選択範囲を確認して**作成**」が実際は主導線と同じ**プレビューを開くだけ**の動作で、文言の動詞が食い違う（即Excel作成と誤解されるリスク）
- 「↩Undo(直前削除)」が「削除操作を元に戻す」とも読め、実際の動作（直前作成したグループを削除する＝作成の取り消し）と逆に取られかねない
- ~~ステータス行に `$A$1:$D$10` のような生のセル参照記法がそのまま表示される~~ **【収束2周目のレッドチームレンズが誤りを指摘・削除】** `app/ui/main_window.py:608` で `sel.Address.replace("$", "")` により既に `$` は除去済みで、この指摘は現状のコードと一致しない（対応不要）
- 描画処理中（`is_processing`）でもヘッダーの「設定▾」「その他▾」内の「図面クリア」「雛形作成」「Undo」がガードされておらず、破壊的操作を選べるように見える
- 埋め込み1窓モード（本線）の方が2窓フォールバックよりライブ更新の説明文が少ない（`!embedded` の場合のみ表示）
- バリデーションエラーは内容自体は具体的（例: 「ID 5: 接続先 99 が見つかりません」）だが、対応するExcelのセルへ導線がない

改善案（一部）: 色の役割を1対1に固定し「今何が起きているか」は色以外（文言・アイコン）で表現する／キャンセル系ボタンは常に灰色に統一し黄色は本当に単発の強調が要る箇所に限定する／メニュー文言を主導線と揃える／Undoラベルを結果主語の表現に変更する。

### P3: 保守性・テスト拡充（【実装レンズ】）

- ボタン状態決定ロジック（`preview_active`/`has_target`/`is_processing`等の4値から「どのSTYLE定数を選ぶか」）を純粋関数に抽出すれば、P0-1のような呼び忘れをユニットテストで機械的に検出できるようになる

- 3系統の独立COMポーリング（1秒`_poll_excel_status`／0.75秒`live_preview`／100ms `embedded_preview._main_pump`）が同一Tkメインスレッドで直列化されており、今回の修正でステータス行ポーリングに「ボタン色更新」という責務が追加され、この既存の結合にさらに依存する処理が増えた（将来の検討事項、緊急ではない）

## 付録: 各レンズの完全な所見

### IxD / UX（体験設計）

> 「Excelで表を選択 → 表を読み込んでプレビュー → 内容確認 → Excelに作成」という一本道のタスクを、初めて触る人が迷わずに完了できるかを検証。認知負荷・エラー回復・状態遷移の一貫性の3点で所見をまとめた。直近修正（ボタン3色化・空状態文言・描画位置オフセット等）はいずれも妥当な改善だが、その上でなお残る/新たに生まれた懸念を挙げる。

- [高] 「Excelに作成」の有効/無効判定とプレビュー画面の表示が食い違いうる（P0-2として上記に集約）
- [中] 「選択範囲を確認して作成」の文言が実際の挙動（プレビューを開くだけ）と食い違う
- [中] メイン「表を読み込んでプレビュー」ボタンの色が、自分が押していない操作（選択範囲メニュー経由）でも変わる（`preview_active` がモード共通の単一フラグのため）
- [中] 3色ボタンの意味を説明する手がかりが画面上にない
- [中] 埋め込み1窓モード（本線）の方が2窓フォールバックより説明が少ない（ライブ更新の説明文が非表示）
- [低〜中] バリデーションエラーからExcel該当セルへの導線がない
- [低] 「キャンセル」と「✋中止」の視覚トーンが揃わない。「キャンセルすればExcelには何も書きません」という安心材料がボタン自体に表れていない
- [低] 「↩Undo(直前削除)」のラベルが動作と紛らわしい
- [低] ステータス行に `$` 記号付きセル参照がそのまま出る
- [低] 描画処理中でもヘッダーメニューが操作可能なまま
