## 0. 症状（ユーザー報告・引き継ぎ）

- 「表の補完」で **ID** の提案→更新は実機 OK（前セッションで一括 Value 不反映をセル単位＋検証に修正済み）。
- **列**および**段**の「提案の計算」が実機でうまく動かない（報告文言は「提案の計算」中心。**一覧が出ないのか、更新でシートが変わらないのかは未切り分け**）。
- 完了定義（引き継ぎ §4）: 列・段で一覧→必要なら更新まで通る、または原因特定＋修正済み。再現手順とログに基づく切り分け記録が残る。

**読み方の注意:** 報告ラベルが「提案の計算」でも、実害が「更新しても Excel が変わらない」なら更新経路の仮説が一次原因になりうる。逆に、一覧が出ない症状に更新経路の修正を当てても直らない。**P1 で一覧の有無を確定するまで、どの仮説も「本命」に固定しない。**

## 1. 仮説一覧（P1 後の候補順 · 現時点は条件付き）

優先ラベルの意味:

| ラベル | 意味 |
|--------|------|
| **条件付き有力（更新）** | 「一覧は出るが更新で見た目の対象セル不変」かつ §2 の A/E 切り分けで A 単独と判定できたとき本命 |
| **条件付き有力（計算）** | 「一覧が出ない／提案 0 件」が観測できたときの本命候補（主に B。E もここに入りうる） |
| **条件付き有力（列レイアウト）** | v1/v2 ずれ（仮説 E）。**一覧なし**でも**一覧あり→更新後**（誤列書き込み）でも昇格しうる |
| **低（配線・黙殺）** | 計算中のまま固着・タイムアウト時の候補。ID が同一セッションで成功していれば棄却しやすい |

### 仮説 A — 書き込みが ID 修正前と同じ「列一括 Value」のまま（条件付き有力・更新）

| 項目 | 内容 |
|------|------|
| **主張** | 列・段の「更新」はまだ `level_writer.write_level_updates` の `target_range.Value = column`（列全体一括代入）。雛形でタイトル行が ListObject 直上に接すると `CurrentRegion` がタイトル＋表に広がり、**例外なしで Excel に反映されない**ことがある。ID で実機確認済みの症状と同系統。 |
| **根拠** | `id_writer.py` 先頭コメント・実装（セル単位＋読み戻し検証）。引き継ぎ §6「列/段書き込みはまだ `level_writer` の列一括 Value」。`level_writer.py` は `target_col` を差し替えて段にも同じ一括代入を使う。書き込み後検証は無く、失敗しても `ok=True, updated_count=N` になりうる（仮説 D）。 |
| **昇格条件（必須）** | 段（推奨）で一覧が出る→更新→**見た目の段セル不変**に加え、§2 の **A/E 切り分け**で v2 期待どおりかつ隣列に誤書き込みがないこと。 |
| **棄却 / 反証** | (1) 一覧が出ない／計算中のまま → 当該報告の一次原因ではない。(2) `isFullMode=false` かつ明示 `rangeAddress` でも更新無反映 → CurrentRegion 混在説は棄却（一括 Value の別因は残しうる）。(3) セル単位書き込みに直しても「提案の計算」症状が直らない → 報告症状の誤診。(4) 隣列だけ変わる／ヘッダが v1 寄り → A 単独ではなく E（または併発）。 |
| **合致する実機症状** | 一覧は出るが更新後シート不変（「N件更新」表示あり/なし）。 |
| **修正の方向（未着手・A 昇格後）** | `id_writer` と同様に提案行だけセル単位＋読み戻し検証へ寄せる。一括でも成功していた表（タイトル非接等）の回帰をテストで残す。 |

### 仮説 B — 空欄判定で提案 0 件（条件付き有力・計算）

| 項目 | 内容 |
|------|------|
| **主張** | JS→Python→計算は成功しているが、対象セルが空欄とみなされず `blank_only` で提案 0 件。「提案はありません。」と見え、「動かない」と感じる。 |
| **根拠** | `parse_level_optional` は `None` / `""` / **パース不能**を空欄（`None`）とする。`0` は有効な段・列で空欄ではない。段の `blank_only` は空欄行だけ連番。 |
| **昇格条件** | 計算後すぐ「提案はありません。」かつ、問題セルが空に見えても実際は `0` や数値。 |
| **棄却** | セルが本当に空なのに 0 件 → 仮説 E（列ずれ）等へ。一覧が出る → B は当該症状の一次原因ではない。 |

### 仮説 E — v2 固定インデックスと v1 表レイアウトのずれ（条件付き有力・列レイアウト）

| 項目 | 内容 |
|------|------|
| **主張** | `_run_proposal_compute` / `write_level_updates` は常に v2 定数（段=`TIER_COL=5`、列=`LEVEL_COL=6`）で生セルを読む・書く。一方 `parse_table_rows` は v1 分岐で段=4・列=5。v1 表では**見た目の段・列と違う列を読んで**非空扱い→提案 0 件、または**別列を更新**しうる。 |
| **根拠** | `proposal_fingerprint.py` の固定定数。`parse_table.py` の v1/v2 分岐。ID は列 0 中心のため v1/v2 に強く依存せず、**「ID は動く／列・段だけおかしい」**報告と相性が良い。 |
| **現れ方（2経路）** | (1) **計算側**: 一覧なし／提案 0 件（手順3）。(2) **更新側**: 一覧は出るが、見た目の段・列は不変で隣列だけ変わる（手順2 の A/E 切り分け）。 |
| **昇格条件** | ヘッダ位置が v2 期待とずれている、または更新後に意図しない列だけ変化。空欄行なのに提案 0（手順3-5①）も昇格材料。 |
| **棄却** | 失敗表が確定 v2 でヘッダと index 5/6 が一致し、空欄行に提案が出る／更新で正しい列だけ変わる／計算が応答しない、など。 |
| **修正の方向（E 昇格後）** | raw 読み書きをパーサと同じ列解決に揃える、または v2 以外を明示エラーにする。 |

### 仮説 C — JS→Python ディスパッチ / 黙殺 return（低・配線）

| 項目 | 内容 |
|------|------|
| **主張** | (C1) `scope` が Python 側で無視・誤分岐。(C2) `_handle_proposal_action` が `request_id` 消費後に `watch` 不在で**結果もエラーも返さず return**し、フロントが「計算中…」のまま。 |
| **根拠（弱い〜中）** | 同一 UI・同一ポーリングを ID と共有。ID が一覧まで通る同一セッションなら、共有ブリッジ断線や watch 欠落は棄却しやすい。ただし ID 成功が保証するのは共有部分までで、列の `compute_level_proposals`（固定点反復）や段/列の `_push_proposal_result` までは保証しない。 |
| **合致する実機症状** | 列・段だけ「計算中…」のまま、または F8 無応答タイムアウト。ログに compute 開始も失敗も無い（C2）。 |
| **注意** | 列の「計算中ハング」は仮説 C 以外に **`level_inference` 本体の長時間**もありうる。段は計算が軽いので、段でのハングは COM/push/ディスパッチ寄り。 |

### 仮説 D — 更新成功表示とシート実態の乖離（A の観測シグネチャ）

| 項目 | 内容 |
|------|------|
| **主張** | 一括 Value が黙って失敗しても `WriteResult(ok=True, updated_count=N)` を返すため、UI は「N件更新」と出るがシートは変わらない。 |
| **位置づけ** | 単独の一次仮説ではなく、A 昇格時の観測シグネチャ。`id_writer` は読み戻し検証あり、`level_writer` は無し。 |

## 2. 切り分け手順（実機 · P1 · 修正前必須）

修正に入る前に実施する。ログがあれば `dist/logs/app.log` の `proposal_compute_failed` / `level_update_write_failed` / `id_update_verify_failed` 近傍も見る。

| 観測 | 解釈 |
|------|------|
| 段で一覧が出る → 更新 → **見た目の段セル不変** | すぐ A 本命にしない。手順2の **A/E 切り分け**へ |
| 段で「提案はありません。」のみ | **B または E**。操作チェックリスト（手順3）へ |
| 列だけ推論不能で要確認だらけ・提案 0 | 列は接続関係依存のためデータによっては正常に提案 0 もありうる。**段**で同手順を優先（段は並び順連番でデータ依存が小さい）。 |
| 計算中のまま／F8 タイムアウト | **C**、列なら `level_inference` 長時間、COM/スレッド例外。同一セッションで ID 計算が戻るかで C2（watch）を棄却/残す。ログの exception を優先。 |

**推奨確認順（コスト小→大）**

1. **段**・空欄が確実な行がある表で「提案の計算」→ 一覧の有無を記録  
2. 一覧ありなら「更新」→ UI メッセージ・**見た目の段セル**・**隣の列（接続先・列・Text 等）の変化の有無**を記録 → 下の **A/E 切り分け**  
3. 一覧なしなら、下の **操作チェックリスト（B/E）** を埋めてから解釈する  
4. 必要ならログで `scope`・例外・compute 痕跡を確認（C / 列推論長時間）

**A/E 切り分け（手順2 · 一覧あり・更新後）**

仮説 E は「別列を書いて、見た目の段・列だけ不変」にもなりうる。次を記録してから昇格する。

| 記録 | A（＋D）単独へ | E 優先または A+E 併発 |
|------|----------------|------------------------|
| ヘッダ位置（色列の有無・段/列の列番号） | v2 期待どおり（段=6列目、列=7列目） | v1 寄り、または段/列の列番号が期待とずれ |
| 更新後、隣の列の値 | 変化なし（対象の段だけ触ろうとして何も残っていない） | 意図しない列だけ値が変わった |
| UI | 「N件更新」等 | 同上でも可。隣列変化があれば E を残す |

**操作チェックリスト（手順3 · 一覧なしのとき）**

隣で操作する人がそのまま埋められるようにする。列番号は **ヘッダ行の左から 1 始まり**（Excel の見た目）。コード上の 0 始まり index は括弧で併記する（記入は 1 始まりのみでよい）。

| # | 確認すること | 自分の表での記録 | 判定の目安（写さない） |
|---|--------------|------------------|------------------------|
| 3-1 | ヘッダ行の並びを左から書き出す | （記入）例: `ID / 図形種別 / 色 / …` | — |
| 3-2 | **色**列があるか | あり / なし | あり→v2 寄り、なし→v1 寄り |
| 3-3 | 「段」「列」は何列目か（1 始まりで数える） | `段=□列目 / 列=□列目` | v2 期待は段=**6**(index 5)、列=**7**(index 6) |
| 3-4 | 問題セルの**数式バー**表示 | 空 / `0` / その他 | — |
| 3-5 | 解釈（上から順に1つ選ぶ） | （該当を○） | ① 3-3 が v2 期待と**ずれ** → **E** ② 3-3 は一致かつ 3-4 が `0`/数値 → **B** ③ 3-3 は一致かつ 3-4 が空なのに提案 0 件 → **追加調査**（B/E 以外） |

## 4. コード上の事実メモ（レビュー用・推測と分離）

- 列インデックス（**提案の raw 読み書きが使う定数**）: 段=`TIER_COL=5`、列=`LEVEL_COL=6`（`proposal_fingerprint.py`）。v2 ヘッダ `TABLE_HEADERS_10_V2` と同順。
- `parse_table_rows` は v1 のとき段・列のインデックスが上記より 1 つ左（仮説 E の根拠）。
- 提案計算: 段=`compute_tier_proposals`、列=`compute_level_proposals`。生セルは `parse_level_optional`。
- 更新: 列・段とも `write_level_updates(..., target_col=...)`。ID のみ `write_id_updates`（セル単位＋検証）。
- UI: `ProposalPanel` の `targets` で id/level/tier 切替。`sendProposalAction` → `window.__proposalAction` → Python ポーリング。
- `_handle_proposal_action`: `request_id` 重複抑止のあと `watch` が無ければ黙って return（結果 push なし）。

## 5. 現時点の推奨（レビュー反映後）

1. **P1 必須**: 段で「一覧の有無」を先に見る。これなしに A 修正へ入らない。  
2. 一覧あり→更新後は **A/E 切り分け**を経てから A 単独 or E/併発を決める（見た目不変だけで A にしない）。  
3. 一覧なしなら操作チェックリストで **B / E** を切り分け、P2b。  
4. ID 修正の成功は「列段も一括 Value が犯人」の証明には使わない（更新経路の類似根拠に留める）。

ポリシー選択は当面なし（切り分け結果で修正ブランチが変わるだけ）。
