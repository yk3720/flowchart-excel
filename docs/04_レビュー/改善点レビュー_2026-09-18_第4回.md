## 2. 改善点一覧（優先度別、依頼者との合意反映済み）

### 今すぐ

1. **F1【重大: 高】ID重複・図形種別空欄・色未知値・段列重複が UI に一切出ない（サイレント失敗）**
   以下がすべて `logger.warning`（ログ）のみで、messagebox・プレビュー画面のどちらにも到達しない:
   - **ID重複行** → 2件目のノードが黙って除外される（`app/core/parse_table.py:135-138`、`seen_ids`）。flowchart-studio 側 `validate.ts:34-40` にも同種チェックはあるが、内部で呼ぶ `parseTable.ts` が重複IDの2件目を検査前にスキップ済みのため**構造的に発火しない死コード**（実装を2周にわたって裏取り済み）。
   - **図形種別が空欄の行** → 黙ってフローから除外（`parse_table.py` 同箇所、`仕様・管理\プロジェクト仕様書.md` 129/307行）
   - **色列の未知値**（`黄`/`橙`/`青`以外） → 無条件・無警告で白塗り（`app/core/flow_colors.py:27-34`）。`validate.ts` の検証対象にも含まれない。
   - **段・列が同一の2ノード**（判断ノードの分岐先の指定ミス等） → 座標が完全一致し図形が重なって片方が見えなくなる（`app/core/layout_preview.py:121-183`、flowchart-studio `layoutGrid.ts:96-140` に衝突検出なし）。`validate.ts` の検証対象にも含まれない。
   - （参考・解消済み）**接続先(下)/(右) が存在しないID** → `validate.ts:42-49` が検出し `generate.ts` 経由で `generated.ok=false` → `window.__flowchartValidation` → `embedded_preview.py` の `is_create_enabled()` が「Excelに作成」ボタンを無効化する。エラー文言（例:「ID X: 接続先 Y が見つかりません」）はプレビュー画面にテキスト表示もされる。**2026-09-17実装のPhase1b(a)で既に解消済み**。
   - 改善案: 残る4点（ID重複／空欄種別／未知色／段列重複）の検知を、既存の `warnings` 集約の仕組み（欠落接続先で既に実装済みのパターン）に合流させ、プレビュー画面またはExcel生成完了時のメッセージボックスに一覧表示する。**ただし表示するだけでは読み飛ばされるリスクがある**ため、「警告がある間はボタンの見た目・文言を変える／作成前に確認ダイアログを挟む」など無視しづらい導線とセットで設計する。改修コスト: 小〜中。

2. **F2【重大: 中】色選択のわかりにくさ**（懸念2そのもの）
   有効な色は `黄`/`橙`/`青` の3種のみ（`flow_colors.py:8-12`）。雛形作成時のデータ入力規則（`main_window.py:_create_template` L680-682, `Validation.Add`）は図形種別列にしか設定されておらず、色列にはドロップダウンが無い。ユーザーは有効な色の存在自体をコードを見るまで知り得ない。
   改善案: 雛形の色列にも `黄,橙,青` のリスト検証を追加（`SHAPE_TYPE_VALIDATION` と同じパターンを1行追加）。改修コスト: 小。ただし**Excelのデータ入力規則はセルのコピー&貼り付けではバイパスされる**点、既存の種別列バリデーションが `r+1`〜`r+100` の固定100行にしか適用されていない点は限界として認識しておく（F1のUI通知と組み合わせれば入力後の検知でカバーできる）。

3. **F3【重大: 中、ただし①②③とも早期着手】判断ノードの段・列設定を助ける機能が無い**（懸念1そのもの）
   段(tier)・列(level)は表の値をそのまま座標に変換するだけで、自動計算・提案・矛盾検証は無い（`layoutGrid.ts:96-140`, `layout_preview.py:121-183`）。埋め込みプレビュー（ライブ更新）が視覚的な確認手段として機能している点は緩和材料だが、「プレビューを見て気づく」以上の補助は無い。
   改善案:
   - ①（F1と共通）段列重複の検知・警告 — 低コスト
   - ②仕様書 or アプリ内ヘルプに「下=同列で段を進める／右=列を変える」の早見表を追記 — ドキュメントのみ、低コスト
   - ③**段・列の自動計算・提案機能** — 仕様変更級の大改修だが、**依頼者の一番の懸念（懸念1）の本命解決であり、早めに設計検討を開始する**（2026-09-18、依頼者と合意）。①②を土台に、まず設計方針（自動計算の対象範囲・UIでの見せ方）を固める段階から着手する。

4. **F6【重大: 中〜高、新規発見】キャンセルのタイミング次第で「中止しました」表示なのに実際は図形が生成されUndo対象からも漏れる**
   `_draw_core`（`app/core/excel_engine.py:271-295`）はキャンセル判定を `place_shapes`/`connect_nodes` 後にしか見ておらず、`finalize_composites`〜`create_final_groups`（286-295行）はキャンセル判定なしに最後まで走る。`_worker_from_snapshot`（`main_window.py:558-566`）は `stop_event.is_set()` なら `last_group_name` への代入をスキップするため、実際にはシート上に完成した1グループが残るのに、アプリは「何も起きていない」ことにし、Undo（↩）でも追跡できなくなる（`last_group_name` はUndo実装 `main_window.py:729-733` が直接参照する唯一の追跡手段）。仕様書（`プロジェクト仕様書.md:274`）の「グループ化失敗時はUndo対象外を警告」はグループ化が**成功**しているこのケースをカバーしない。
   改善案: `create_final_groups` 直前でも再度キャンセル判定するか、中止分岐でも `group_name` が非空なら `last_group_name` に設定する（後者は小改修）。ユーザーの元の懸念4点には含まれないが、**改修コストが最小でありながら「操作を信じられなくなる」実害度が高く**、本レビュー全体で費用対効果が最良の項目。

### 近いうち

5. **F5【重大: 中】行追加時にID・接続先の手直しが必要**（懸念4そのもの）
   採番・renumber・接続先自動追随のロジックはコードベース全体で見当たらない。手直しミス（IDズレ・既存IDと衝突・存在しない接続先）はF1のサイレント失敗経路をそのまま通る。フル自動採番はライブプレビューがタイマーポーリング方式（COM SheetChangeイベントフック無し）のため、ユーザーの編集操作との競合リスクがあり高コスト。
   改善案: まずF1の可視化（重複ID検知をUIに出す）で代替する。フル自動化は様子見（下記）。

6. **F4【重大: 低〜中】行の入れ替え・挿入を助ける機能が無い**（懸念3そのもの）
   雛形はExcelネイティブテーブル（`ListObject`, `main_window.py:668`）のため、行挿入・並べ替え自体はExcel標準機能で可能（現場ユーザーにとって大きな障壁ではないとの評価あり）。ただしテーブル内挿入時に新規行へF2のデータ入力規則が自動継承されるとは限らない。単独の実害は小さいが、F5と組み合わさると「挿入したら壊れたのに理由が分からない」体験になる。
   改善案: 単独実装より、F1・F5とセットで再評価。専用UIより自動追随・警告の方が費用対効果が高い。

7. **F8【重大: 低】プレビュー（WebView2）が無応答のまま止まると、作成ボタンが理由不明のまま永久に無効**
   `_poll_validation` にタイムアウトが無い（`embedded_preview.py:254-278`）。データ破損リスクは無いが操作性の問題。
   改善案: 数秒無応答でステータス欄に「プレビューが応答していません」等を表示。

### 様子見

8. **F5のフル自動採番・自動追随**（上記5の本体） — 改修コスト大・COM競合リスクがあるため、F1可視化後の実運用状況を見て判断。
9. **F7【重大: 低〜中】Excel/COMクラッシュ時、アプリ側ロールバックは機能せず、生成前の保存導線も無い**
   `_rollback()`（`excel_engine.py:221-226`）はCOM呼び出し依存でExcelプロセス死亡時は無力。生成開始前に保存を促す導線がコード全体に無い。発生頻度が低い異常系のため、着手するとしても最後でよい。

## 付録: 判明した技術的事実（詳細）

### ID重複検証が構造的に機能しない経路（新規発見）
`flowchart-studio/lib/flowchart/model/validate.ts:34-40` は次の処理を行う:
```
const { nodes } = parseTable(table, schema);   // ← 既に重複IDが除外された後
const idSet = new Set<string>();
for (const n of nodes) {
  if (idSet.has(n.id)) errors.push(`ID ${n.id} が重複しています`);  // 到達不能
  idSet.add(n.id);
}
```
`parseTable.ts:44-48` の `seenIds` が2件目以降のIDを `continue` でスキップしてから `nodes` に積むため、`validate.ts` が受け取る時点で重複IDは存在せず、37行目のエラー文は構造的に発火しない。Python側 `app/core/parse_table.py:135-138` も同じロジック（`seen_ids`）で、警告はログのみ。

### 接続先未解決の検知（解消済み）経路
`validate.ts:42-49` → `generate.ts`（`errors.length>0` で `ok:false`）→ `preview-web/src/App.tsx`（`window.__flowchartValidation = {ok, errorCount}`）→ `app/ui/embedded_preview.py` の `_poll_validation`/`_on_validation_js_result` → `is_create_enabled()` が `validation_ok` を要求 → ボタン無効化。エラー文言はプレビュー画面のヘッダーにも常時表示される（`embedded` フラグに関わらず）。2026-09-17実装、[第3回レビュー](改善点レビュー_2026-09-16_第3回.md) §6参照。
