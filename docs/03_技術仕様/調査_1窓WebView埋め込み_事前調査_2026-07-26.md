## 1. 調査スコープ

| 論点 | なぜ必要か |
|------|------------|
| CTk/tk と pywebview の同居 | 現状は別プロセス。1窓埋め込みは同一プロセス化が論点 |
| Tk Frame への WebView2 埋め込み | 「操作＋プレビュー」同一レイアウトの本命手段 |
| Excel COM の複数スレッド | ライブ更新・ステータス・描画の競合 |
| Zオーダー／前面 | Excel クリックでプレビューが消える問題 |
| 配布（WebView2 Runtime · PyInstaller） | exe 利用者環境 |

## 2. 障害マップ（あたり）

| ID | 障害 | 重大度 | 現状コードとの関係 |
|----|------|--------|-------------------|
| **H1** | **pywebview は tk Frame 埋め込み非対応**（メンテナ明言） | Critical | 現行 `preview_host` は独立 `webview.start` |
| **H2** | **tk `mainloop` と `webview.start` は双方ブロッキング** — 同一スレッド同居不可 | Critical | Staff レビュー Critical と同型 |
| **H3** | 同一プロセス化すると **Excel COM（STA）** へステータス／ライブ／描画が集中し競合 | Critical | 現状はプロセス分離で緩和されている |
| **H4** | HWND 宿主の WebView2 は **airspace（常に前面レイヤ）** 問題がありうる | High | 埋め込み時、ボタンが WebView 下に隠れるリスク（主に WPF 文献だが HWND 宿主共通） |
| **H5** | 埋め込み代替（tkwebview2）は **js_api 相当が弱い／要 STA スレッド** | High | 現行 preview-web の `pywebview.api.confirm` 契約と不整合の恐れ |
| **H6** | WebView2 Runtime 未導入マシン | Medium | `have_runtime` / インストール誘導が必要 |
| **H7** | 絶対「常時最前面」は他アプリ作業時に鬱陶しい | Medium | 製品約束は体験ゴールに留める（仕様 §6） |

## 3. 技術ルート比較（POC 候補）

レビューで挙げた A/B/C を、調査結果で具体化したもの。

### ルート C — 別プロセス維持 + 疑似1窓（**一期 POC 推奨**）

| 項目 | 内容 |
|------|------|
| **内容** | CTk 操作 UI を薄くし、プレビュー WebView を主画面化。または操作も HTML 化せず、**レイアウト上「一つの作業セット」**に見せる |
| **前面問題** | 子 WebView に `on_top=True`（[pywebview On Top](https://pywebview.flowrl.com/examples/on_top)）で Excel 作業中も背面化しにくくする。必要なら Excel フォーカス検知で一時切替 |
| **利点** | **H1/H2 を回避**。現行アーキテクチャ延長。ライブ更新・js_api を維持 |
| **欠点** | OS 的には2ウィンドウのまま。完全な「1 HWND」ではない |
| **POC 判定** | Excel クリック後もプレビュー継続 + 本線 CTA 整理が可能か |

### ルート A — Tk Frame に WebView2 を HWND 子として埋め込み

| 項目 | 内容 |
|------|------|
| **候補ライブラリ** | [tkwebview2](https://pypi.org/project/tkwebview2/)（WebView2 を Frame に載せる）· [tkwry](https://github.com/mashu3/tkwry)（wry `build_as_child` · 単一 mainloop · IPC） |
| **制約** | pywebview 本体は埋め込み非対応（[#405](https://github.com/r0x0r/pywebview/issues/405) · [#1360](https://github.com/r0x0r/pywebview/issues/1360)） |
| **tkwebview2** | STA 必須 · Runtime 検出あり · **js_api 弱さの報告あり**（Issue #1360 コメント）→ `evaluate_js` / 独自ブリッジ要設計 |
| **tkwry** | 設計思想が「Tk の Frame 内に Web」— 有力だが **Rust/maturin・新しさ・社内配布検証**が必要 |
| **利点** | 真の1窓レイアウト |
| **欠点** | 依存追加 · js_api 再実装 · CTk との相性検証 · H3/H4 |
| **POC 判定** | CTk フレーム内で preview-web 表示 + Python←→JS 往復 + リサイズ |

### ルート B — UI を pywebview（または単一 Web シェル）に寄せ、tk を縮小／廃止

| 項目 | 内容 |
|------|------|
| **内容** | 操作 chrome も HTML/React 側へ。Excel COM だけ Python ホスト |
| **利点** | 二重 mainloop 解消 · studio フロント資産と近い |
| **欠点** | CTk UI の作り直しが大きい · 一期スコープ超過リスク（PM「やらないこと」に抵触しやすい） |
| **POC 判定** | 最小シェル（読込・作成ボタン + プレビュー）だけ Web 化できるか |

## 4. 障害ごとの解決方針

### H1 / H2 — 埋め込みと mainloop

| 解決 | 内容 |
|------|------|
| **短期（推奨）** | ルート C。`create_window(..., on_top=True)` で背面化を緩和。操作パネルは小さく／統合レイアウト |
| **中期** | ルート A で tkwebview2 または tkwry の POC。js ブリッジを先に試作 |
| **避ける** | 同一スレッドで `root.mainloop()` と `webview.start()` をネスト起動（SO・FAQ で失敗例多数） |

### H3 — Excel COM

| 解決 | 内容 |
|------|------|
| 公式 | Office OM はスレッドセーフではない · STA で呼び出しが直列化される（[Threading support in Office](https://learn.microsoft.com/en-us/visualstudio/vsto/threading-support-in-office?view=vs-2022)） |
| Python | スレッドごとに `CoInitialize` · オブジェクトを生で渡さず **marshal**（`CoMarshalInterThreadInterfaceInStream` 等） |
| アプリ設計 | **Excel アクセスを単一ワーカー／キューに直列化** · 描画中はライブ停止 · busy 時はリトライ／スキップ |

### H4 — airspace / Zオーダー

| 解決 | 内容 |
|------|------|
| 認識 | HWND 宿主 WebView は他コントロールの上に張り付く事例が WPF で多い（[WebView2 WPF](https://learn.microsoft.com/en-us/microsoft-edge/webview2/platforms/wpf)） |
| Tk 埋め込み時 | プレビュー領域と操作領域を **重ならせないレイアウト**（上下分割・左右分割）を基本にする |
| 前面維持 | OS 最前面は `on_top` で足りることが多い。絶対最前面は製品として約束しない |

### H5 — js_api

| 解決 | 内容 |
|------|------|
| 現行維持なら | ルート C のまま `pywebview.api` 継続 |
| 埋め込み時 | `window.chrome.webview.postMessage` / `evaluate_js` / tkwry IPC のいずれかで **confirm・refresh・setPayload** を再定義 |

### H6 — Runtime

| 解決 | 内容 |
|------|------|
| 起動時 | Runtime 有無チェック · 無ければ案内（tkwebview2 の `have_runtime` / `install_runtime` 相当） |
| 配布 | 社内 Win10/11 は多くの場合プリインストールだが、チェックリストに残す |

## 5. 推奨進め方（実装着手時）

1. **POC はルート C から**（障害 H1/H2 を踏まずに、要望の「消えない」「前面絞り」を先に満たす）  
2. 並行で **ルート A の小さいスパイク**（空 HTML + JS 往復）を 0.5〜1 日で試し、真の1窓の実現可能性を記録  
3. ルート A が通れば二期で埋め込み本線化。通らなければ C を製品形として固定  
4. いずれのルートでも **COM 直列化**と **作成時スナップショット**は P1〜P2 で必須
