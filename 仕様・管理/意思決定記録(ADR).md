# 意思決定記録 (ADR)：MZ0000_FlowchartTool rev014

## [ADR-001]：GUIライブラリ選定（customtkinter）

- **ステータス**: 承認済み
- **文脈・問題**: 
  - フローチャート作成ツールのGUIを実装する必要があった
  - 標準の`tkinter`は見た目が古く、モダンなUIを実現するには不十分
  - `PyQt5`や`Kivy`は依存関係が重く、配布（exe化）時のサイズが肥大化する懸念
- **選定理由**: 
  - `customtkinter`は`tkinter`を拡張した軽量ライブラリで、モダンなUIを実現できる
  - 依存関係が少なく、exe化時のサイズ増加が最小限
  - Windows環境での動作が安定している
  - 角丸ボタン、カラーテーマ等のUI要素が標準で提供されている
- **捨てた選択肢の欠点**: 
  - **PyQt5**: ライセンス（GPL）の制約、依存関係の肥大化、学習コストが高い
  - **Kivy**: モバイル向け設計でデスクトップアプリには過剰、依存関係が複雑
  - **標準tkinter**: 見た目が古く、モダンなUI要素（角丸、カラーテーマ）の実装に手間がかかる
- **帰結**: 
  - 軽量でモダンなUIを実現できたが、一部の高度なUI要素（アニメーション等）は実装できない
  - 将来的にUIの大幅な拡張が必要になった場合は、PyQt5への移行を検討する必要がある

## [ADR-002]：Excel COM操作の実装方式

- **ステータス**: 承認済み
- **文脈・問題**: 
  - Excel上にフローチャート図形を描画する必要があった
  - Excelファイルの読み書きだけでなく、図形の作成・配置・接続が必要
  - COM操作は複雑で、エラーハンドリングが重要
- **選定理由**: 
  - `win32com.client`を使用してExcel COMオブジェクトに直接アクセス
  - 図形の作成、コネクタの接続、グループ化等の高度な操作が可能
  - Excelのネイティブ機能を最大限活用できる
  - 既存のExcelワークブックに直接描画できるため、ユーザーのワークフローに自然に統合できる
- **捨てた選択肢の欠点**: 
  - **openpyxl**: 図形（Shape）の作成・操作ができない、読み書き専用のライブラリ
  - **xlsxwriter**: 図形操作が限定的、既存ファイルへの追記ができない
  - **外部画像生成（PIL/Pillow）**: Excelに貼り付ける手間、ベクター形式ではないため拡大時に劣化
- **帰結**: 
  - Excelのネイティブ機能を活用できたが、Windows環境に限定される
  - COM操作のエラーハンドリング（`pywintypes.com_error`）が必須
  - Excelが起動している必要があるため、バックグラウンド処理は困難

## [ADR-004]：非同期処理の実装方式（threading）

- **ステータス**: 承認済み
- **文脈・問題**: 
  - Excel COM操作は時間がかかる場合があり、UIをフリーズさせない必要がある
  - 処理中にユーザーが中断できる機能が必要
  - GUIライブラリ（customtkinter）はメインスレッドで動作する必要がある
- **選定理由**: 
  - `threading.Thread`を使用してCOM操作を別スレッドで実行
  - `threading.Event`（`stop_event`）で中断信号を管理
  - `self.after()`でGUI更新をメインスレッドに委譲
  - I/Oバウンド処理（Excel COM操作）には`threading`が適している
- **捨てた選択肢の欠点**: 
  - **asyncio**: GUIライブラリ（customtkinter）が非同期対応していない、COM操作との相性が悪い
  - **multiprocessing**: プロセス間通信のオーバーヘッドが大きい、Excel COMオブジェクトの共有が困難
  - **同期処理**: UIがフリーズし、ユーザー体験が悪化
- **帰結**: 
  - UIの応答性が向上し、中断機能も実現できたが、スレッド間の同期（`self.after()`）が必要
  - COM操作のエラーハンドリングが複雑になったが、`try-finally`で確実にクリーンアップ

## [ADR-005]：ログ出力方式（構造化ログ）

  - **JSON形式**: 可読性が低い、ファイルサイズが大きくなる
  - **無制限ログ**: ログファイルが肥大化し、ディスク容量を圧迫
- **帰結**: 
  - ログの解析が容易になったが、フォーマットが固定されているため柔軟性に欠ける
  - ログファイルの管理が自動化され、運用負荷が軽減された

## [ADR-015]：flowchart-studio 準拠デザイントークンの導入（rev002追加）

- **選定理由**: 
  - customtkinter を維持したまま、`flowchart-studio/app/globals.css` の `--flow-*`（Layer C 操作 chrome）トークンを色の SSOT として `app/constants.py` に移植（`FLOW_ACCENT` `#2563eb` 等）

  - 機能グループを白背景+1px枠線のカードに統一し、shadcn の card パターンを模す
  - Excel COM 操作ロジック（`app/core/`）は無改変。UI 層のみの変更に閉じる
- **捨てた選択肢の欠点**: 
  - **Tauri/Electron + React で作り直す**: `flowchart-studio` と同一コンポーネントを使えるが、Excel COM 操作を Rust/Node 側で再実装する必要があり大規模。`tauri-practice`（2026-06-27 決定）で「flowchart-studio 本体への Tauri 統合は当面しない」と既に判断済みで、本アプリ単独での採用も同じ論点（工数・保守対象の増加）を抱える
  - **配色を個別に微調整**: SSOT が定まらず、将来 `flowchart-studio` 側の配色が変わるたびに追随できない
- **帰結**: 
  - 両ツールの配色言語（青=主要操作、赤=破壊的操作、スレート系ニュートラル=背景）が揃い、同じ製品群であることが視覚的に伝わるようになった
  - コンポーネント形状（角丸ボタン vs shadcn の角丸カード等）までは一致しないが、色・枠線・階層のルールは共通化された
  - `flowchart-studio` 側で `--flow-*` の値を変更した場合、本リポの `app/constants.py` も追随して更新する必要がある（自動同期はなし、手動同期が運用上の負債）
